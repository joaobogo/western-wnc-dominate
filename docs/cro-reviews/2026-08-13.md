\* homepage run-to-run variance is high (4.2s–5.4s across runs); the hero cross-fade
is the LCP candidate. \*\* no LCP entry recorded in that run.

CLS is effectively zero everywhere (well under 0.1). INP ranged 32–1560 ms under 4x CPU
throttle; the outliers are on pages with heavy motion sections.

Fixes shipped this cycle:
- Responsive AVIF/WebP `srcset` (640/1024/1600) on the homepage hero and the roofing,
  replacement, repair, storm, and construction hero images — a 390px phone now pulls a
  ~640px file instead of the 1600px master.
- Route speculation moved behind `load` + idle, staggered one route at a time, and
  skipped entirely on `saveData` / 2G. It was previously firing during page load and
  competing with the LCP image.
- `lucide-react` bundled into a single `icons-vendor` chunk. The build was emitting
  hundreds of one-icon files, which starved the connection under high-latency mobile —
  the single biggest win (~0.9–1.4s off LCP on service pages).

Remaining gap: every page is still above the 2.5s LCP target on this deliberately harsh
profile. The bottleneck is now JS execution, not bytes — first paint waits on the
292 kB main chunk plus React and framer-motion. Real-world 4G/H2 numbers will be
materially better; re-measure against the published domain before spending more here.

## 5. Next three prioritized changes
1. **Trim the initial JS chunk** (mechanism: earlier first paint → lower bounce on
   entry pages). Move `towns` and nav data out of the eager path and lazy-load
   framer-motion for below-fold sections.
2. **Recovery prompt targeting** (mechanism: recover exits that were leaving anyway).
   After one cycle of data, restrict it to the page types where show→callback beats
   1.5% and drop it elsewhere.
3. **Town + service form start rate** (mechanism: reduce the leap from read to
   commit). Test an inline two-field callback block above the local FAQ against the
   current full form link.
